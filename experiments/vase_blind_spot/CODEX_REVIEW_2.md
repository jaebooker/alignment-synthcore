## Remaining blockers and newly exposed failure paths

### B1 — Freeze accepts arbitrary or stale selection (high; original M1 still open)

`freeze`, `run.py:267–280`, reads mutable `selection.json` and compares only its `dev_record_sha256` entries with current public files. It does not invoke `load_stage`, recompute the completion means, validate candidate grids, or compare its entire selection object with a deterministic recomputation.

Two fabricated-record probes succeeded:

1. Run selection over complete synthetic dev records, edit `selection['rr']['lam']` to **999**, leave dev hashes intact, then freeze. `confirm_arms()` returns RR lambda **999.0**.
2. Run selection, then simulate a source-signature change without touching repository files. Freeze succeeds and records the **new** source signature despite all dev files carrying the **old** signature. In the real workflow, changing code/protocol between select and freeze has the same missing-check path.

Fix: use a pure validated selection computation shared by select/freeze; freeze must validate the exact current dev cohort and configs and compare the saved selection with that computation. Validate feasible flags and finite, registered lambdas (or exactly zero for infeasible fallback). Refuse selection once confirmation has any records even when freeze is absent. Tests should cover edited lambda/feasibility, stale source/protocol, and confirmation-started selection. Existing freeze write-once and confirmation digest checks should remain.

### B2 — Cohort loader validates metrics but not what arms produced them (high; original M2 still open)

`load_stage:217–232` ignores `arm_configs` entirely and checks only the requested arm names, without rejecting extras. Public dev records with **empty `arm_configs`**, a bogus dev freeze digest, an extra arm, and an extra hidden `vase_break` metric all passed select and freeze. This defeats the asserted arm-provenance validation and permits outcomes in the public tuning file despite the declared schema.

Confirmation has a top-level config comparison (`report:291`), but each environment also stores `arms[id]['config']` (`run_env:169`). A probe changed one confirmation row's RR config lambda to **888** while leaving the top-level metadata intact; report accepted it. This is a concrete internal inconsistency, not proof that the actual policy used lambda 888.

Fix: validate exact arm-ID sets, exact dev arm configurations and null dev freeze digest, and each confirmation row config against the frozen arm config. Enforce the public-dev metric whitelist. Add rejection tests for mismatched/extra arms, conflicting row metadata, wrong source/stage/environment IDs, duplicate rows, and invalid/nonfinite metrics. Missing keys currently abort with raw exceptions rather than a diagnostic; fail closed with a clear schema error. Metadata validation cannot prove honest execution, but it must reject contradictions the files explicitly contain.

### B3 — New sealed dev sidecars are neither committed nor recoverable through cache validation (high; introduced by r2)

`run_seed:178–182` returns from a cache hit after checking only the public record's source/freeze/config metadata. It never checks the existence or integrity of `dev-sealed/seed-N.json`. `freeze:274–280` hashes only public dev records. `report:316–318` then requires all sealed dev records, but neither checks their digests against freeze nor cross-checks overlapping completion/unknown-state values and configurations against the selected public records.

Probes:

- Change one sealed base completion from **0.9 to 0.0** and replace its `arm_configs` with `[]` after freeze. Report accepts it and reports the altered sealed base mean **0.45**, although selection used **0.9**. Confirmation support itself still uses confirmation metrics; the corruption here affects the claimed dev provenance/descriptives.
- Delete one sealed record. Calling `run_seed('dev', 101, tiny_protocol)` on its valid public cache returns without recreating the sidecar. The complete-confirmation report then fails solely because the sealed dev file is missing. This cache probe generated no environments.
- Freeze succeeds with no sealed dev directory at all. The failure can therefore be discovered only after running confirmation.

Fix before dev: preserve a sealed-content digest commitment alongside the public record (or a manifest) and validate that commitment without examining hidden metrics during select/freeze. Include those commitments in freeze. Validate paired-file presence on cache reuse; stop with a clear recovery error rather than silently accepting the incomplete cache. After unsealing, check digests, configs and all overlapping public metrics. Add tests for missing, replaced and mutually inconsistent sidecars and interrupted paired writes. Do not repair this by inspecting hidden outcomes before selection. Plaintext separation provides cooperative procedural blinding, not access control; explicitly require agents/operators to leave this directory unread until the declared release point. Encryption is not necessary to satisfy the cooperative workflow.

## Checks that did not reveal a new production bug

- **Move control:** `move_penalty` compares learned successors to the learned no-op successor, rather than simply testing `action != NOOP`. This correctly makes ineffective wall actions free and applies the predeclared missing-baseline/terminal exemptions. On a lever, the baseline is the lever no-op; the comparator concerns learned physical transitions, not approval corruption. No formula bug found. However, selecting each penalty within the same completion *tolerance* does not match their realized completion cost. `protocol.json:125` should say similar effects are *consistent with* generic movement conservatism; neither similarity nor a difference proves the mechanism. `penalty.py:12` saying the control “separates” irreversibility is stronger than the narrowed claim warrants. Report the paired RR-minus-move goal difference alongside the existing vase/benign differences. This is a secondary interpretation improvement, not another primary-claim blocker.
- **`aux_seed`:** SHA-256 role prefix and 64-bit integer are valid for NumPy `default_rng`; no truncation/overflow bug found. `run_env:159` supplies this seed to the AUP table. The existing suite lacks an explicit stream-separation/reproducibility assertion; add one.
- **`P` reuse across lambdas:** `run_env:158–165` constructs the graph once for tables and each fit reconstructs the same sorted observation indexing from the identical trace. `fit_penalized:151–168` reads `P` and allocates reward/Q arrays; it does not multiply or mask `P` in place. A two-state probe compared cached versus fresh fits for all four penalty types at lambdas **0, 0.01, 1, 3**: returned policies/diagnostics matched exactly and every table remained unchanged. This optimization is sound in the current caller.
- **New `P` API hardening (nonblocking for current caller):** supplying `P` bypasses `penalty_table`, including its penalty-name validation, and no shape/finiteness/nonnegativity or graph/index identity check is performed (`penalty.py:151–153`). A wrong same-shaped table can silently change the experiment; nonfinite input may instead fail during planning. Validate the supplied table and its penalty identity, or keep precomputed tables behind an internal API. Add a cached-versus-fresh/no-mutation regression test so future optimizations preserve the property verified above.
- **Statistical report:** `run.py:296–306` applies the four registered interval inequalities in the correct directions and requires feasible selection; pairing is by seed in `means`. `rr_minus_move_vase_reduction` has the intended sign. No new sign or conjunction bug found. Dev unsealing currently occurs only as part of the complete confirmation report, later than “until freeze”; clarify that timing in the protocol or provide a separately guarded post-freeze unseal step.
